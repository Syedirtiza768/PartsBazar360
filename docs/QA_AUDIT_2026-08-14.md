## A. Executive QA Summary

**Overall health: good architecture, one half-finished migration, several real correctness bugs.**

The marketplace's fundamentals are strong: the search page is server-rendered with the URL as the single source of truth (filter state, pagination and sort survive refresh, back/forward, and URL sharing by construction); multi-select filter logic is verifiably correct (OR within a facet, AND across facets — confirmed live: BOSCH 1,593 + VALEO 139 = 1,732 combined, and category intersection narrows correctly to 81); facet counts are scoped post-filter and agree with actual totals (verified live, 44 = 44); checkout order creation is genuinely idempotent (session-bound idempotency key, `P2002` replay recovery, resume/retry of existing orders, `PaymentAttempt` audit rows); both client-side async flows that exist (autocomplete, staged-filter count preview) use debounce + `AbortController` correctly.

**Major risks, in order:**

1. **A half-finished search migration is the dominant systemic issue.** Two search stacks are live simultaneously and disagree: the buyer-facing `/api/search/parts` reads the legacy `canonical_parts` index (107,565 docs), while `/api/v1/search` reads the `parts_search` alias → `canonical_parts_v3` (**296,157 docs — roughly 187k more documents than the 108,621 parts that actually have an active offer**). The same query returns different totals on the two paths (`alternator`: 408 vs 511). If the frontend is ever switched to v1 without fixing the v3 corpus rule, buyers will see large numbers of unbuyable parts.
2. **Relaxed-search pagination is broken live.** When a query has no strict matches, page 1 shows relaxed results with a large total (e.g. 7,917) — but page 2+ re-runs the strict query, returns `total: 0`, and the UI renders "No matching parts — try removing a filter". The buyer is told results exist and then that none exist, one click apart.
3. **Vehicle identity has duplicate, indistinguishable configurations.** 66 vehicle generations have multiple `VehicleConfiguration` rows that are identical in every buyer-visible field (trim/engine/transmission all NULL), and fitment data is attached inconsistently across the twins (observed: 0 vs 2, 0 vs 6 fitments on twins; live Corolla configs of one generation returned 52 / 162 / 164 / 165 parts). The same vehicle selection can produce different result sets depending on which duplicate row the picker resolves — a direct violation of the audit's core determinism principle.
4. **Deep pagination silently caps the catalog.** Browse-all has 107,565 results but the 100,000 result window caps offset pagination at ~99,975 items (page 1,333 at pageSize 75); ~7,500 listings are unreachable by browsing. Worse, requests beyond the window return `total: 0` rather than the real total, so a hand-edited or stale URL presents the entire catalog as empty.

**Most important UX issues:** misleading "No parts match" empty states (relaxed page 2+, out-of-range pages, beyond-window pages); fitment-mode "Showing 1–75 of 98" label while only 24 items render (API ignores `pageSize` in vehicle mode).

**Most important backend issues:** divergent search corpora; browse latency regularly 0.5–1.2 s (target < 400 ms); vehicle taxonomy queries repeatedly cancelled by timeout (`57014`) in `SeoCatalogService`; fitment search responses of ~852 KB for 24 items because each item embeds hundreds of fitment config IDs.

**Most important consistency problems:** two different search APIs with different shapes and different data; fitment vs browse response envelopes differ (no facets/maxPage/totalRelation/relaxed in fitment mode); `pageSize` honored in browse but ignored in fitment.

## C. Full QA Findings

### QA-01 — Relaxed search pagination collapses to zero on page 2+

- **Area:** API / Search
- **Severity:** P1
- **Environment:** production, any browser
- **URL:** `/search?q=xyzzy+brake+pad` (any query with zero strict matches and many relaxed matches)
- **Preconditions:** a query whose strict match set is empty but whose relaxed set is large
- **Steps:** 1. Search `xyzzy brake pad`. 2. Page 1 shows "No exact matches — showing related parts", total 7,917, pagination visible. 3. Click page 2.
- **Expected:** page 2 continues the relaxed result set.
- **Actual:** `GET /api/search/parts?q=xyzzy+brake+pad&page=2` returns `{total: 0, relaxed: false, items: []}`; UI renders "No matching parts — try removing a filter".
- **Evidence:** live probe 2026-08-14: page 1 → `total=7917 relaxed=true`; page 2 → `total=0 relaxed=false`.
- **Root cause:** `OpenSearchService.browseParts` only applies the relaxed retry when `pageNum === 1` (`apps/api/src/modules/search/opensearch.service.ts` ~line 790). The comment says this keeps pagination "consistent with the page-1 total", but it does the opposite: page 1 reports the relaxed total while deeper pages use the strict query and report 0.
- **Recommended fix:** carry the relaxation decision through the request — e.g. compute strict-total once per query (cheap, `size: 0`), cache it in the Redis search cache for ~60 s, and use the relaxed clause on every page when the strict set is empty. Add `relaxed` to the cache key.
- **Affected components:** `opensearch.service.ts` (`browseParts`), `search.controller.ts`, `app/search/page.tsx` (empty-state messaging).
- **Regression risk:** medium — relaxation also feeds facet aggregation via the `qClause` closure; the fix must rebuild aggs under the same clause used for hits on every page.
- **Regression tests:** API integration test — relaxed query, pages 1–3, same non-zero total and `relaxed: true` on all pages; no duplicate IDs across pages.

### QA-02 — Two divergent live search stacks (legacy index vs v3 alias)

- **Area:** Search / API / Ops
- **Severity:** P1
- **URL:** `/api/search/parts` vs `/api/v1/search`
- **Steps:** 1. `GET /api/search/parts?q=alternator` → `total: 408`. 2. `GET /api/v1/search?q=alternator&pageSize=24` → `pagination.totalResults: 511`, `meta.index: "parts_search"`. 3. On the server: `_cat/indices` shows `canonical_parts` (107,565 docs, **yellow**) and `canonical_parts_v3` (**296,157** docs); `_alias/parts_search` → `canonical_parts_v3`.
- **Expected:** one search contract serving buyer-visible parts (parts with ≥1 active offer: 108,621).
- **Actual:** buyer traffic reads the legacy index; the promoted alias points at v3, which contains ~187k more documents than parts with active offers — i.e. v3 includes large numbers of parts with nothing to buy. v1 warm latency ~1.05 s vs 23 ms measured on the v2 candidate.
- **Root cause:** the v2→v3 rollout changed indexing scope (v3 appears to index the full 274k-row catalog rather than the buyer-visible subset), and the alias was promoted without the frontend or the old endpoint being migrated. `docs/SEARCH_PHASE2_RESULTS.md` §5 warned the alias was *not* promoted and `/api/v1/search` not deployed; both are now live without the documented validation (facet counts unverified, response-shape compatibility unverified).
- **Recommended fix:** decide the single buyer-visible rule (`EXISTS active offer` + buyer-visible-offers util), rebuild v3 against it, re-run the §2 acceptance probe on v1, then migrate `/search/parts` to the v1 service (or retire v1 and port its parser/ranking into the legacy service). Do not leave both public. Fix the yellow legacy index (0 replicas on a single node).
- **Affected components:** `search/index/*`, `search/v1/*`, `search/opensearch.service.ts`, reindex CLIs, `docs/SEARCH_PHASE2_RESULTS.md` runbook.
- **Regression risk:** high — this is the storefront's core query path; stage behind the probe CLI + a measured rollback window as the existing runbook prescribes.
- **Regression tests:** the existing `probe-search-v2.cli.js` acceptance set against whichever index serves `/api/search/parts`; corpus-guard test (index doc count within ±5 % of `parts with active offer`).

### QA-03 — Duplicate vehicle configurations break fitment determinism

- **Area:** Database / Vehicle compatibility
- **Severity:** P1
- **Steps:** 1. SQL: 66 generations have ≥2 `VehicleConfiguration` rows with `trim`, `engine`, `transmission` all NULL. 2. Their fitment attachment diverges (twins with 0 vs 2, 6 vs 0 fitments). 3. Live: three all-null Corolla configurations of one generation returned totals 162, 164 and 165; a Hilux twin pair returned 98 and 1.
- **Expected:** one configuration per buyer-distinguishable vehicle; selecting "2018 Toyota Corolla" yields one deterministic result set.
- **Actual:** which duplicate row the picker/URL resolves determines the result set; duplicates are indistinguishable in the UI.
- **Root cause:** missing unique constraint on `(generationId, trim, engine, transmission)` (with NULL-normalization), and fitment write paths attaching to whichever config row their import created rather than a canonical one.
- **Recommended fix:** add a normalized unique index; merge each duplicate group into the config with the most fitments (re-point `Fitment.vehicleConfigId`, delete empties); make the vehicle picker and `searchCompatibleParts` resolve through one canonical config per generation when the row is otherwise indistinguishable.
- **Affected components:** `vehicle` module, `ingestion`, `mvl-oe-recovery-job.mjs`, Prisma schema.
- **Regression risk:** medium — fitment re-pointing must run in one transaction per group; salvage/fitment UIs read the same table.
- **Regression tests:** integration test — every generation has exactly one all-null config; fitment count for a vehicle is identical via picker and direct URL.

### QA-04 — Result window caps browse and falsifies totals

- **Area:** API / Search
- **Severity:** P1 (correctness of what the catalog claims), practically P2 reach
- **URL:** `/search?page=1400&pageSize=75`
- **Steps:** browse-all `total=107,565`, `maxPage=1333` (window 100,000). Page 1,334+ returns `{items: [], total: 0}`.
- **Expected:** either the full catalog is reachable (cursor/`search_after` pagination), or the UI honestly communicates the cap and the API never reports `total: 0` for a non-empty query context.
- **Actual:** ~7,500 listings unreachable by browsing; beyond-window pages claim the catalog is empty. The frontend caps pagination links at `maxPage`, but stale/shared/search-engine URLs can exceed it.
- **Root cause:** offset pagination against OpenSearch `max_result_window` with a graceful-empty guard that returns `total: 0` instead of the true total (`opensearch.service.ts` ~line 735).
- **Recommended fix:** short term — return the real total with empty items and a `pageOutOfRange: true` flag, and have the frontend clamp (redirect to `maxPage`). Long term — `search_after`/PIT cursor pagination for deep pages.
- **Regression tests:** API test — page beyond window returns true total + flag; E2E — hand-edited `?page=9999` lands on a valid page with correct count.

### QA-05 — Fitment mode ignores `pageSize`; range label lies

- **Area:** API + Frontend contract
- **Severity:** P2
- **URL:** `/search?vehicleConfigId=<id>`
- **Steps:** the frontend always sends `pageSize=75` (`app/search/page.tsx` `getResults`); the fitment branch of `search.controller.ts` only reads `limit` and defaults to 24. Live verification: Hilux config `b0de0674…` — `total=98, limit=24`, 24 items.
- **Actual:** the page renders "Showing 1–75 of 98" above 24 cards; page 2 is labeled "76–98 of 98" while returning items 25–48. (`rangeStart/rangeEnd` use the frontend `pageSize`, pagination math uses `results.limit` — two different values.)
- **Root cause:** one endpoint, two page-size parameters, fitment branch ignores the one the frontend sends.
- **Recommended fix:** honor `pageSize` in the fitment branch exactly like browse (alias of `limit`, same 200 cap).
- **Regression tests:** contract test — fitment search with `pageSize=75` returns `limit: 75` and up to 75 items; UI range label equals actual slice.

### QA-06 — Out-of-range page shows a misleading empty state

- **Area:** Frontend / UX
- **Severity:** P2
- **URL:** `/search?q=brake+pad&page=99`
- **Steps:** force a `page` beyond the result count (stale bookmark, back-button after filter change via edited URL, search engine).
- **Actual:** `items: []` with `total > 0` renders the "No parts match / try removing a filter" empty state — the filters did match; the page number didn't.
- **Recommended fix:** in `app/search/page.tsx`, when `results.total > 0 && items.length === 0`, `redirect()` to the last valid page (or render a "This page is out of range — go to page N" state). Do not reuse the zero-result empty state.
- **Regression tests:** E2E — out-of-range page recovers to a valid page with results and preserved filters.

### QA-07 — Sort orders lack a final `_id` tiebreaker

- **Area:** API / Search
- **Severity:** P2 (latent)
- **Steps:** all `browseParts` sort clauses end at `createdAt desc` (and fitment at `minPrice asc`); live probe showed page-1/page-2 boundary prices tied at 15.71 (three items).
- **Actual:** no duplicates observed in a same-second probe, but any tie spanning a page boundary can swap order across index refreshes (segment merges), producing duplicates/disappearing items between pages — exactly the failure class the brief targets.
- **Recommended fix:** append `{ _id: { order: 'asc' } }` (or a `uid` tiebreak) to every sort clause in `browseParts` and `searchCompatibleParts`.
- **Regression tests:** paginate a tied sort key across 3 pages twice with a forced refresh between; assert identical ordering and zero duplicates.

### QA-08 — Fitment search responses are ~35 KB per item (852 KB for 24)

- **Area:** API / Performance
- **Severity:** P2
- **Evidence:** `GET /api/search/parts?vehicleConfigId=…&page=1` → 851,971 bytes for 24 items; each item embeds a `fitments` array of hundreds of vehicle-config UUIDs (one FEBEST slide pin carried 400+ IDs).
- **Actual:** the buyer card needs none of these IDs; payload size delays first render on mobile and multiplies Redis cache memory.
- **Recommended fix:** strip `fitments` (and `partNumbers` internals like `createdAt/updatedAt/canonicalPartId`) from search items in `sanitizeSearchItems`, keeping only what `ProductCard` renders.
- **Regression tests:** snapshot the search-item shape against `lib/types.ts` `Part`; payload-size budget test (< 150 KB per 75-item page).

### QA-09 — Browse latency regularly exceeds targets

- **Area:** Performance
- **Severity:** P2
- **Evidence:** production API logs, 2026-08-14: recurring `Slow browse` warnings 513–1,184 ms on ordinary queries (categories, browse-all, part numbers); v1 warm query 1,052 ms. Phase-2 targets were p95 < 400 ms.
- **Recommended fix:** profile the slow shapes (facet aggregations over 100k+ docs are the likely cost — consider `includeFacets: false` for deep pages, pre-aggregated facet caches for filter-less browse, and the v2/v3 explicit mapping once QA-02 lands). The 45 s Redis cache helps repeats but not first-hit长尾.
- **Regression tests:** latency budget assertion in the probe CLI (p95 < 400 ms over the acceptance query set).

### QA-10 — Vehicle taxonomy queries repeatedly cancelled by timeout

- **Area:** Backend / SEO surfaces
- **Severity:** P2
- **Evidence:** API log burst, 2026-08-14 11:32: ~10 `SeoCatalogService — Vehicle taxonomy query failed: canceling statement due to user request (57014)` within seconds — the windowed aggregation over `VehicleConfiguration`/`Fitment` is slower than the caller's timeout, so `/vehicles/…` landing-page data intermittently fails.
- **Recommended fix:** precompute/cache taxonomy aggregates (the sitemap path already uses cached windowed chunks — reuse the pattern), and add a statement-timeout budget with a fallback rather than surfacing a cancelled query.
- **Regression tests:** taxonomy endpoint p95 budget test; error-path test that a slow aggregation degrades to cached data.

### QA-11 — One endpoint, three response shapes; v1 a fourth

- **Area:** API contract
- **Severity:** P2
- **Actual:** `/search/parts` returns `{items,total,page,limit,maxPage,facets,relaxed,totalRelation}` for browse, `{items,total,page,limit}` for fitment (no facets/maxPage/totalRelation), `{total,totalRelation}` for `countOnly`, `{parts,categories,…}` for suggest; `/api/v1/search` returns `{query,results,facets,appliedFilters,pagination,corrections,meta,requestId}`. The frontend's `BrowseResponse` papers over this with optional fields.
- **Recommended fix:** when QA-02 converges the stacks, publish one envelope (`items/total/totalRelation/page/limit/maxPage/facets/relaxed`) and keep fitment mode inside it (empty facets array rather than absent keys). Document `countOnly` and suggest as explicitly separate contracts.
- **Regression tests:** shared zod/class-validator schema test asserting every search response validates.

### QA-12 — 2,102 part numbers identify more than one canonical part

- **Area:** Database
- **Severity:** P2
- **Evidence:** SQL: 2,102 `CatalogPartNumber.normalizedNumber` values map to >1 distinct `canonicalPartId`.
- **Context:** this is the known MPN-merge problem space (decision log 2026-08-14 documents the brand-blind merge repair). Remaining shared numbers mean some searches/cards can still surface fragmented or cross-brand identity.
- **Recommended fix:** complete the repaired-merge pass; enforce brand-namespaced MPN matching on future merges (already decided — this is the execution gap).
- **Regression tests:** data invariant — no normalized number spans multiple canonical parts unless flagged as a verified cross-reference.

### QA-13 — Staged price label hardcodes "$"

- **Area:** UX
- **Severity:** P3
- **Evidence:** `lib/filter-params.ts` `priceStateLabel` returns `$${min}-$${max}`; catalog currency is AED and a currency switcher exists elsewhere.
- **Recommended fix:** route the label through the shared currency formatter.
- **Regression tests:** unit test on label rendering per active currency.

### QA-14 — Autocomplete navigates via legacy UUID route

- **Area:** Frontend / SEO
- **Severity:** P3
- **Evidence:** `HeroSearch.tsx` `navigateToPart` pushes `/part/${id}` — a permanent 301 hop to `/parts/<slug>`, adding a redirect to a primary navigation path.
- **Recommended fix:** include `slug` in the suggest payload and link directly.
- **Regression tests:** suggest E2E asserting a single-hop navigation.

### QA-15 — Index hygiene drift

- **Area:** Ops / Data consistency
- **Severity:** P3
- **Evidence:** legacy `canonical_parts` is yellow (1 replica on a 1-node cluster) and drifts ~1k docs from the DB truth (107,565 vs 108,621 parts with active offers); `canonical_parts_v3` carries 31,416 deleted docs.
- **Recommended fix:** 0 replicas on single-node; run the reconcile CLI on a schedule (outbox is fully drained — 257,144 DONE, 0 PENDING — so the pipeline now works); force-merge or rebuild v3 after the QA-02 decision.
- **Regression tests:** nightly reconcile job reporting drift > 2 % as an alert.

### QA-16 — Deploys produce a brief error window

- **Area:** Ops
- **Severity:** P3
- **Evidence:** during the 2026-08-14 API container restart, several `/api/*` calls returned HTML error pages (nginx 502/504 during the down window) and `SeoSlugService` logged slug-hydration timeouts; search tiles fell back to UUID links.
- **Recommended fix:** rolling/blue-green deploy or `update.sh` health-gated swap so nginx never routes to a booting container.
- **Regression tests:** deploy runbook check — synthetic probe must return JSON 200 throughout a deploy.

### Verified working (no defect)

- Repeated identical queries return identical totals and identical item order (live A/B probe).
- Multi-select OR within facet, AND across facets; facet counts equal actual filtered totals (44 = 44 live).
- Filter changes reset pagination (`buildHref` drops `page`); clear-filters preserves the query; URL is the single state source; refresh/back/share are consistent by construction.
- Checkout idempotency: session-bound key, existing-order resume, `P2002` replay recovery, payment retry creates `PaymentAttempt` rows, webhook claim prevents duplicate confirmations.
- Autocomplete and staged-filter count previews: debounce + `AbortController` + stale-response guards — no race found.
- Search outbox fully drained; all write paths enqueue through it.
- Search URLs are `noindex,follow` with canonical consolidation to taxonomy pages; PDP slug resolution has a UUID fallback.

## D. Determinism Report

> Can the same user action reliably produce the same result every time?

**Mostly yes for keyword search and browse — no in four places:**

1. **Relaxed searches** — page 1 and page 2 of the same result set disagree (QA-01).
2. **Vehicle selection** — duplicate configurations make the same vehicle resolve to different result sets (QA-03); the same generation's configs returned 52/162/164/165 parts.
3. **Deep pages** — page ≤1333 works, page 1334+ reports an empty catalog for a 107k-result query (QA-04).
4. **Sort ties at page boundaries** — no unique tiebreaker, so ordering can shift under index refresh (QA-07; latent, not observed live).

Caching (Redis 30–60 s + Next ISR 30 s) means a listing change can take up to ~90 s to appear — bounded and acceptable, but two refreshes inside the window can legitimately differ; this is the one deliberate staleness trade-off.

## E. UX Consistency Report

- **Fitment vs browse mode** behave as two different products: different page size handling (QA-05), no sort control, no facets, different response shape (QA-11). Justified partially by design, but the range-label bug is not.
- **Empty states**: three distinct situations (no matches / relaxed matches / page-out-of-range) collapse into one misleading "No parts match" message (QA-01, QA-06).
- **Currency display**: filter staging uses `$`, the rest of the marketplace uses AED/switcher (QA-13).
- **Part links**: cards and PDPs use slugs; autocomplete uses UUID + redirect (QA-14).
- Everything else reviewed (chips, pagination control, sort select, drawer, quick-filter dropdowns) follows one pattern via `filter-params.ts` shared helpers — a genuine single source of truth.

## F. Frontend/Backend Contract Issues

1. `pageSize` sent but ignored in fitment mode (QA-05).
2. `BrowseResponse.facets/maxPage/totalRelation/relaxed` all optional because fitment responses omit them (QA-11).
3. Search items carry fields the frontend never consumes (`fitments` ID arrays, `partNumbers` audit columns) — over-fetch (QA-08).
4. `Part.fitments` is typed `Array<string | PartFitment>` — two different wire shapes under one field name; works, but it's exactly the kind of union that drifts.
5. v1 response shape shares no field names with the legacy envelope (`results/pagination.totalResults` vs `items/total`).

## G. Root-Cause Groups

- **RC-A: The search migration is half-done.** Symptoms: QA-02 (dual stacks), QA-09 part (v1 latency), QA-15 (index hygiene), the docs/runbook mismatch. Fix the rollout, not the symptoms.
- **RC-B: Pagination correctness was designed for page 1.** Symptoms: QA-01 (relaxed page 2), QA-04 (window cap), QA-06 (out-of-range UX), QA-07 (tiebreakers). One pagination contract (cursor or honest offset + clamp + tiebreak) fixes all four.
- **RC-C: Vehicle identity lacks a uniqueness invariant.** Symptoms: QA-03 and the MVL-recovery edge cases it feeds.
- **RC-D: Fitment mode is a parallel mini-implementation.** Symptoms: QA-05, QA-08, QA-11. Converge it into the browse path with a fitment filter.
